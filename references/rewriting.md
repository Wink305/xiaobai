# 改写长文的具体手法

用户贴一大段 AI 生成的文字、方案、报告，让你"看懂"或"整理"。这类任务比直接回答更容易出错，因为你在动别人的东西。

核心原则：**改的是表达，不是事实和立场。** 原文说什么就是什么——除非原文自己错了，那时标出来，不替他改。

## 动笔前先判断

| 情况 | 怎么办 |
|---|---|
| 原文观点清楚，只是啰嗦 | 直接压缩，观点不动 |
| 原文有事实错误 | 压缩 + 标出错误 + 说明"这条我按原样保留了" |
| 原文自相矛盾 | 标出"这两句对不上"，**不要**挑一个信、更不要替他抹平 |
| 原文立场偏激 / 推销 | 保留立场，但把"应该"和"事实"分开写 |
| 原文是别人写的、有署名 | 改写时保留出处，不要写成好像是你写的 |
| 用户说"帮我润色"而不是"看懂" | 这是两种活：润色要保留全部信息量，看懂可以砍。问一句 |

## 顺手查一下原文漏了什么

改写长方案时，除了压缩，还要做一件原文没要求的事：**对照 `references/domains.md` 看这个领域有没有该领域必有的硬信息，而原文漏了。**

判断方式：把原文的主题代进 domains.md 的各节里，看有没有"这一类东西通常必须有、原文中一个字没提"。

发现问题时的处理——**单独成段，明确标注这不是原文的内容**：

```
另外有一条原文没写、我提出来给你确认的：
赠送金额算不算销售额、要开发票还是开收据？这个涉及真金白银，原文里没提到。
```

三件事都不能省：

- **标出"原文没写"** — 否则用户会以为原方案里有这回事
- **说清是"要确认"不是"要你做"** — 你在提示，不是在替他加决策
- **只加会出事的** — 不加"建议补充验收标准""建议优化用户体验"这类锦上添花

原因：用户把压缩版当依据去执行。原文漏掉的硬信息，他不会自己去想到。**但你也不能默默塞进去**——那既是他没做的决定，又让他误以为原方案考虑过。

反过来也一样：原文提了但你判断不重要的硬信息，**不要删**。改写是改表达，不是改风险偏好。

## 压缩的优先级

按这个顺序砍，先砍掉的可以放心：

1. **重复** — 同一个意思在结论、正文、总结里各说一遍，保留信息最全的那次
2. **过程叙述** — "我们首先分析了…接着考虑了…最后决定…"，小白只需要结果
3. **自我论证** — "这个方案的优势在于…同时它也具备…"这类没有新增信息的对仗句
4. **他明确说不关心的** — 他说"我就知道要做什么"，原理和选型理由都可以砍

**不能砍**（按 A/B 分级处理）：

- 结论、决策项、责任人、时间点
- 数字、金额、日期、版本号
- 前提条件、限制、风险
- 原文里的"不"字和"但是"—— 砍掉限定词会把话说反

## 保留还是改造结构

| 原文结构 | 怎么办 |
|---|---|
| 有清晰标题层级 | 压平。小白读标题层级会以为是目录大纲，直接给要点 |
| 是表格 | 转成文字行。窄屏横向滚动是最劝退的阅读姿势 |
| 是代码 / 配置 | **原样照抄，一个字符都不动**，只在前面加一句它在干嘛 |
| 超过 5 节 | 合并到 3 节以内，或者砍掉 B 类内容进挂起区 |
| 顺序是按技术逻辑排的 | 重排成"先说他要做什么" |

## 要不要告诉用户"这是改写版"

**要**，但只用一行，放在最开头。

```
下面是这 800 字的压缩版，原文观点没动。
```

原因：不说明的话，用户会以为这是重新生成的内容，后续引用或转发时会当成你的判断。一行成本很低。

例外：用户明确说"别废话直接给"，那就直接给。

## 改写后的自查

- 原文每个**结论**都还在？（不是每个句子，是每个结论）
- 原文的**限定词**还在？"可能""通常""部分"没被改成"一定""所有"
- 原文的**数字**逐个核对过？
- 原文有**立场**的地方，改写后立场还是原来的立场？
- 有没有**默默替用户做判断**？"我觉得这个方案不行"不能出现在改写里
- 改写后用户**能做出和读原文时一样的决定**吗？

## 挂起区怎么用

改写任务里挂起区尤其重要——原文往往是几十页，你只讲了核心结论。**把砍掉的部分点名列出来**，让用户知道你没漏。

```
我压成了 5 句，观点一个没删。

还有三块我先没展开：
1. 预算那部分（原文 12-15 页）
2. 实施排期（原文第 4 章）
3. 风险清单（原文第 6 章）

想看哪块？
```

**不要只说"更多内容请参考原文"** —— 用户正是读不下去才让你改的，让他回去读原文等于没改。

## 常见错误

| 错误 | 后果 |
|---|---|
| 把改写写成"总结" | 丢掉限定条件和例外，读者据此做决定会出错 |
| 顺手修正原文的错 | 用户不知道你改过；发现时已经不信任整份文档了 |
| 改写后丢掉原来的不确定性标记 | 原文说"待确认"，改写变成肯定句，风险从读者转嫁给你 |
| 把挂起的内容静默省略 | 用户以为全文都讲过了，漏掉的关键信息会出事 |
| 保留原文的华丽措辞 | 改写后还是难读，等于没改 |
| 默默补上原文漏掉的硬信息 | 用户以为原方案里有这回事；补错了他照着做，删了他不知道 |
| 把"给推荐"理解成可以替用户判断 | 改写里你的推荐 = 你的立场。要给推荐就归因到原文 |
