# 帮小白判断和拍板

vibe coding 的人最常卡住的不是"看不懂这个词"，而是**"AI 让我选，我凭什么选"**。

选项翻译成白话了，他还是判断不了——因为他判断不了技术优劣。这份文件解决的是这个。

## 小白判断不了的 vs 判断得了的

**判断不了**（别问他）：哪个技术更先进、哪个架构更好、哪个性能更高、这个框架比那个好在哪。这些问题的答案不取决于他，问了等于没问，只是把焦虑从你转给了他。

**判断得了**（问他这些）：哪个贵、哪个快、哪个以后想换更难、哪个做错了能改回来、他的业务有没有这个需求。

**转换的办法**：把技术问题翻译成业务问题。

```
❌ "数据库用 Postgres 还是 MongoDB？"
   —— 他答不了。两个都是"专业数据库"，他没有任何判断依据。

✅ "你以后会不会经常改蛋糕的规格（比如加一个'定制款'字段）？
    会 → 选 A，以后加东西不用重做。不会 → 选 B，简单省事，反正现在存的也不多。"
   —— 他答得了，而且他的答案直接决定选哪个。
```

**但他如果说"不要问我，你定"——听他的，直接定。** 这时不要再抛业务问题回去。四个维度的理由加一个"什么情况下该换"就够了，够他判断你靠不靠谱、错了能不能退出。

（例外：涉及钱、签字、绑卡、不可逆操作、对外承诺的决定，他说"你看着办"也还是要摆出来——签字的是他。）

**为什么要用业务问题问他**：他答"会经常改"时，选型依据来自他自己的业务，比你替他硬推的结论准。他答不出来时，问题是你问错了，不是他笨。

## 四个可判断维度

推荐时给理由，只用这四个维度，不要用技术优劣：

| 维度 | 白话问法 | 为什么小白判断得了 |
|---|---|---|
| **钱** | 这个要不要额外花钱？以后还要一直花吗？ | 他付过账 |
| **时间** | 哪个能更快看到东西？要等多久？ | 他数过日子 |
| **可逆性** | 做错了以后能不能改回来？改起来要多久？ | 他怕做错，这是核心焦虑 |
| **依赖** | 以后想换掉它，会牵连多少别的东西？ | 他知道牵一发动十 |

**可逆性对小白最重要，因为他一定会做错。** 能反悔的方案即使当下不是最优，也是好方案。选不可逆的方案时，必须明说"这个以后改起来麻烦"。

## 什么时候不该问，该自己定

有些决定问了也是白问，因为**选择依据不取决于他**。这种情况下直接定，然后说清楚。

- "用哪个数据库" — 除非他有明确的业务约束，否则你该自己选
- "要不要加日志" — 除非他要求极简，否则该加
- "用不用 TypeScript" — 小白的项目规模通常都不大，你该选错风险低的

这样做的理由：他答不了的时候，给选项等于把决策成本甩给他，他只能瞎选。**你选一个并承担解释责任，比让他选一个然后都错要好。**

说了自己要做决定时，要带上这两句：
- **为什么选它**（一句话，用上面四个维度）
- **什么情况下该换**（一个他能自己判断的信号）

```
数据库我帮你选了 A，因为以后你想加新字段不用重做。
如果你半年后开始加很多新种类、改结构改到烦了，就该换成另一种——
那时候改会有点麻烦，但不至于推倒重来。
```

## 最黏的选择要重声警示

有些决定不是"以后改麻烦"，是**"改不动"**。选这类之前必须在开头明确说出来，不能混在别的决定里一笔带过：

- **登录方式** — 用户习惯之后改，他们只会记得"点一下就进来了"
- **已经积累的数据** — 换平台时如果不支持导出，等于从零重做
- **已经发出去的承诺** — 对客户的合同、已经收的钱、已经答应的事
- **对外的标识** — 域名、账号名、用户记住的路径

```
**这一条你要知道**：登录方式一旦有学员用习惯了，就别想改了——
他们只会记得"点一下就进来了"。这几样里数这条最黏，所以是我替你要的。
```

把它挑出来单独说，比埋在一堆决定里诚实。用户事后知道和事前知道，结果完全不同。

## 钱的决定：交回去，但不罗列

涉及钱、签字、绑卡的动作，**必须他自己点头**。但这和"不要罗列一堆选项让他挑"会撞上。解法是**选一个，把成本摆出来，只留一个签字动作**：

不要这样（把焦虑原样退回去）：
> 方案 A 每月 30 元，方案 B 每月 80 元，方案 C 买断 600 元。您选哪个？

这样（你选好了，他只做一次决定）：
> 我选了按月付的那种。每月扣多少以平台当天价目为准，我不猜数给你。
> 部署是自动扣款、绑你卡的——**让 AI 把"选哪家、每月扣多少、绑谁的支付方式"发给你看一眼，认可了再开。这一步签字的是你。**

区别：前者要他做评估，后者只要他做确认。**小白做得了确认，做不了评估。**

另外：**技术侧的金额和工期也不许编。** 部署月费、认证费、备案时长这些，写"以平台当天价目为准""要等不少天"，不要给一个看起来合理的数。他会拿那个数去做预算。

## 标出哪些决定是他的，哪些是你的

用户说"你看着办""都行""你决定"时，你在替他做决定。**这时候必须标出来**——否则他以为是自己选的，出问题时会觉得是你坑他。

```
我按"简单、能快点看到东西"来定，先这么做：
- 用最简单的那个方案
- 不加暂时用不到的功能

这个是我的判断，不是必须的。你要是觉得哪里不对劲，说一声我改。
```

反过来，如果某个决定**必须**他来拍（比如涉及钱、涉及对客户的承诺、涉及不可逆操作），即使他说"你看着办"，也要把选项和一个推荐摆出来——因为他签的是字，承担的是后果。

## AI 总结的可信度

用户拿到一段 AI 写的总结，不知道能不能信、有没有漏。**主动标出三件事**，不要等他问：

**1. 哪些是原文就不确定的**
把"待确认""视情况而定""尚未定义"原样带过来，不要抹平成肯定句。

**2. 哪些是你加的**
你补充的推测、和原文不一致的判断，单独标出来。没有标注的补充，他会当成原方案本来就有的。

**3. 哪些是没提但可能要问的**
最容易被漏、又最容易出事的一类。判断方法：拿这份总结对照 `domains.md` 的通用项——这一步要花多少钱、要等多久、谁来做、做错了能撤回吗、有没有时限、怎么判断做成了。

```
这份总结漏了没说的一件事：没提退款规则。
你的方案里如果客户要退，定金怎么算、退不退，这个不定下来会很难谈。
```

## 小白的一句真话

小白说"我不懂，你决定"，往往是在说**"我害怕选错"**。这时候：

- 不要只回"好的我帮你定"然后默默做完 —— 他会一直不放心
- 也不要把所有选项摆出来让他选 —— 那是把焦虑原样退回去
- 正确做法：**你定 + 说理由 + 说风险 + 给一个"什么时候该改"的信号**

这样他既不用猜，又知道以后出问题的出口在哪。
