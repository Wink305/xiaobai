# 改一个正在被别人用的东西

和"从零做"完全不同：这个东西**已经在跑，每天都有人用**，而改坏了的后果落在别人身上。

**这一类最容易被漏掉。** `broken.md` 管的是"坏了怎么修"（他一个人在坏），`shipping.md` 管的是"做出来发出去"（从零）。中间这一档——**改一个活的、别人在用的系统**——没有文件接。

## 先承认一件事：他的怕通常是对的

他如果说"我不太敢动，怕弄坏了大家都用不了"——**这个判断是对的，不要绕过去。**

先给这一句，再给方案。原因：你绕过去他也会犹豫，而且犹豫中会做更糟的事（硬上、或者干脆不做了事）。**先确认他的判断正确，他才会听后面的。**

## 四条红线

不管改什么，这四条先摆出来：

- **别重装、别重置、别跑迁移、别动存数据的那部分**
- **先改副本，不改原件**
- **一次只改一处，改完就停**
- **避开大伙都在用的时间窗**

**这份清单不属于故障流程。** 它绑在"改活系统"上，而不是绑在"用户慌了"上——**数据是好的、用户很冷静的时候，这四条恰恰最该在**，因为唯一会误触数据的正是这次改动。

## 改之前：先弄清数据在哪

你需要知道数据存在哪里才能判断风险，但**不要问他"你用的什么数据库"**——他答不了。

用他能观察的迹象：

| 问他这个 | 说明什么 |
|---|---|
| 大家打开的时候要填网址或登录吗？ | 要 → 数据在服务器上，**改代码不影响数据**，但动服务器配置就会 |
| 断网了还能用吗？ | 能 → 数据在本地，**改代码就可能动到数据** |
| 东西是在哪台电脑上？ | 他知道是哪台，但不知道数据是不是只在那台 |
| 有没有别人在别的地方也在录数据？ | 有 → 多人共用一个地方，改动影响所有人 |

**"填网址"和"要登录"是最有效的一问**——答得出来，而且答完你就能判断大半。

**但这里有个前提不能跳过：复制副本只隔离了代码，没隔离数据。** 数据在云端的时候，复制文件夹等于没隔离。**先确认数据在哪，再说"做个副本"**——否则他会得出"我安全了"的错误结论，然后放心地去改原件。

## 损害落在别人身上 = A 类

这类风险**不参与 A/B 分级**，直接就是 A 类：

- 改坏了 = **同事的工作停摆**
- 别人填的数据 = **公司财产，也是他的责任**
- 别人的账号 = **他的操作被影响，别人会来找他**

判据不是"他会不会亏"，是"**损害会不会落到他以外的人身上**"。会，就是 A 类，没有例外。

## 不是只有他一个人能拍板

公司内部工具，问一句"**这个公司知道你在维护吗**"。可能需要报备，可能有别人也在用，可能数据归属根本不是他的。

这不是走流程，是**改了之后出事他一个人扛**。

## 副本 = 沙箱 + 考题 + 备份

一次动作干三件事：

- 复制整个文件夹，名字加上今天的日期，原件一点不动
- 在副本上改——**前提是数据不在里面**（先确认）
- 改完能自己验一遍：老样子能用吗？新功能能用吗？

## 上线那一刻

改副本他一个人能判断。**换到原件上是另一件事**——别人正在用。

避开早晚上班时间，换之前告诉一声，换完确认一次。这些不用写成清单，**说一句"避开大伙都在用的时候"就够了**。
