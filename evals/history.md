# 迭代历史

记录这个 skill 真实翻车过两次，以及当时怎么修的。**规则不是设计出来的，是被这些坑逼出来的。**

---

## v1.0 首版

### 用例：蛋糕店老板

**用户原话**：

> 我是开蛋糕店的，想在微信上卖蛋糕，帮我弄个能下单的商城。我不会写代码，也没钱请人。太复杂的我搞不定，你直接告诉我第一步该干什么就行。

选这个场景的原因：用户明确说"不会写代码""没钱请人"，非技术信号极强；同时开网店在现实中存在真实的证照门槛，能验证"硬信息有没有被漏掉"。

**结果：失败。**

产出控在 162 个中文字符，漂亮地守住了当时所有的形状规则——结论先行、一个决策、术语全翻译、无表格、无代码块、长度在 200 字以内。

**但整段没提《食品经营许可证》。** 蛋糕属于食品，微信小店和微信支付都会查这张证。

实际后果：她会先去注册小店 → 资质核验不通过被打回 → 严重的话是无证经营。

同期不加载 skill 的 baseline（约 400 字）反而抓到了这条，并把"第一步"正确地定义成查这张证。

**为什么会这样**：当时 SKILL.md 把 200 字写成硬上限，但没有区分"解释性内容"和"阻断性事实"。篇幅压力一来，模型优先砍掉的是看起来最像"可省略细节"的前置条件——而实际上它是唯一不砍就不能用的东西。

这违反了 skill 自己写的"短 ≠ 少信息"。**规则写得再漂亮，答错了就是答错了。**

### 修复

1. Procedure 新增第 1 步：**动笔前先列硬信息**
2. Failure handling 新增：篇幅与硬信息冲突时硬信息赢；事后发现漏了要直接补，不要顺着改口
3. `references/jargon-plain.md` 新增"证照与资质"整节——第一轮模型自己发现这张表没有营业执照 / 食品经营许可证，导致临场编类比
4. SKILL.md 加入这个反例，作为常驻提醒

**第二轮结果：通过。** 列出 5 条硬信息，全部进最终答案：

| # | 硬信息 | 缺了她会怎样 |
|---|---|---|
| H1 | 食品经营许可证 | 资质核验被打回；无证经营违法 |
| H2 | 营业执照 | 连店铺都开不出来 |
| H3 | 收款卡户名须与执照经营者一致 | 货收到却提不出钱 |
| H4 | 费用真相（不写代码 / 开店免费 / 有保证金和手续费） | 她"没钱请人"，默认要花钱会先花冤枉钱 |
| H5 | 顺序不可逆：证没过就停下 | 在一个开不起来的店上白做一堆图和活动 |

字数：全部正文 369 字，其中硬信息 209 字，非硬信息 160 字。

**唯一判断分歧**：H4 的保证金具体金额没有核实，agent 选择显式说"我不给你编数字"并给出查询路径，而不是编一个看起来合理的数字。这是规则直接驱动的行为，也是本 skill 相对 baseline 的差异点——baseline 直接给了"几十到一两百"这类量级描述。

## v1.1 去掉字数上限 + 引入挂起

### 用例：服装店老板

**用户原话**：

> 我开服装店的，想搞个线上卖衣服的地方，让老客户能在微信里直接下单。我不会写代码，也没钱请人。**你别给我整一大篇规划**，我就想知道第一步干什么。

换场景的原因：蛋糕店是"有真实证照门槛"，这个用来验证另一件事——**去掉字数上限后，长度会失控吗？**

**结果：挂起机制成立，但暴露了"硬信息不分级"的问题。**

验证通过的部分：

- 挂起区用了"编号 + 点名 + 边界"写法，用户说"讲第 2 块"能唯一定位到「衣服怎么拍照上架：拍几张、尺码怎么写、要不要开退换货」
- 第二轮 518 字分 8 个短块，用户点名要详细也没有退化成文字墙——每块能独立执行，不依赖上一块读完
- 第二轮只答"怎么弄"，不解释"为什么拍照重要"（用户问的是怎么弄）
- 保留了 2 处显式不确定（服饰类目退货规则差异、异常订单风控），没有装全知

失败的部分（agent 自己如实记录的）：

> 556 字对一个只问"第一步干什么"的人来说仍然偏长。**代价是她读完第一屏仍不知道第二天干什么。**

根因：动笔前列了 8 条硬信息，把整个开店流程的门槛一次性全倒出来了。她只问了第一步，答案却把第 3 步、第 5 步的门槛也摆上来。

这正是"一大篇规划"真正的来源——不是字数多，是**该给的信息和不该在这一轮给的信息混在一起**。

### 修复：硬信息按"卡住哪一步"分级

第 1 步新增分级：

- **A 类（现在就卡）**——缺了迈不出他问的那一步。前置证照、开户、平台准入、这一步要花的钱。写进正文。
- **B 类（后面才卡）**——缺了拦住后面的某一步，但不影响这一步。写进挂起区，等他问到再给。

判断方法：**把 A 类去掉，用户问的那一步还能不能迈出去？** 能，就属于 B 类。

自检清单同步加了一条硬判据：**"用户读完之后，知道今天具体做什么吗？"** 不知道就是没写完——这比字数检查准得多。

### 附带发现

- 挂起区**必须编号**。评测里 agent 自己发现这是成败关键：用户的追问原话是"第 2 块"，如果挂起区不编号，这句话就无法定位，等于把问题推回给用户。
- 挂起区**要点名到小问级别**（"拍几张、尺码怎么写、要不要开退换货"），这样用户即使不说"第 2 块"也能对上号。
- **反向硬信息也算硬信息**：这个场景里 agent 主动写了"服装不需要食品经营许可证"——防止她照着卖吃的教程去办证。少办一张证也是白跑。

## v1.2 新增改写路径 + 跨领域 + 英文

### 用例：会员系统方案改写

**用户原话**：

> 这是 AI 给我写的会员系统方案，太长了看不懂，你就告诉我要干什么就行。（粘贴 2000 字方案：背景、架构、储值档位、等级权益、风险、排期、收益）

选这个场景的原因：改写是 skill 的第二大任务类型，v1.0/v1.1 **从未测过**。而且这份方案故意埋了三个陷阱：概述说 6 周但排期写到 11 周、概述提了数据看板但排期没留时间、投入 15 人日做 4 个模块看着不匹配。

**结果：主体通过，但暴露出两个真问题。**

做对的：

- 逐节核对了结论，一个没丢
- 限定词原样保留（"财务部门测算""可能""建议""待运营团队细化确认"），没把"建议"改成"应该"
- **主动挑出原文三处矛盾并声明"我没替它抹平"** —— 这正是想要的行为
- 数字全部对上（4 档金额、赠送比例、4 级门槛、11 周排期、灰度 10%、收益三项）
- 两件 A 类硬信息进了正文：1000 档赠送比例待财务负责人批、储值资金池存管待法务确认
- 挂起区三条，全部编号 + 点名 + 标注原文出处

暴露的问题：

**1. 规则冲突。** SKILL.md 第 5 步说"给推荐 + 一句为什么"，`rewriting.md` 说"不要替用户做判断"。改写场景下这两条直接打架——agent 只能临场取舍。

修复：第 5 步加例外条款——改写任务里推荐必须归因到原文（"原文建议提到 15%"），`rewriting.md` 优先。

**2. 改写长方案时的漏检。** agent 指出原文完全没提"赠送金额怎么开票/计税""储值款有无有效期和退费规则"——储值是预付性质，这两条是真金白银的坑。但它选择不加，理由是"改写是改表达不改事实"。

这个取舍其实有道理，但暴露了规则缺口：**用户把压缩版当执行依据，原文漏掉的硬信息他不会自己想到。**

修复：`rewriting.md` 新增"顺手查一下原文漏了什么"一节——对照 `domains.md` 检查该领域必有的硬信息，漏了就单列一段，**明确标注"原文没写，这是我要加的"**，只加会出事的，不加锦上添花。

## 沉淀下来的判断

1. **守住规则 ≠ 答对。** 形状合规和内容正确是两件事，必须分别检查。
2. **有上限就有挤出效应。** 任何硬性长度限制都会把某些内容挤出去，所以要先给最重要的东西占位，而不是写完再压。
3. **字数上限是坏判据。** 它逼模型砍掉前置条件（蛋糕店），也逼模型把全流程门槛一次性倒出（服装店）。"删了会不会做错事"比数字准。
4. **"不要编数字"比"给个大概"有用。** 小白场景下，编出来的数字会被直接拿去付钱。
5. **术语表要覆盖真实场景。** 第一轮只写了开发/商业术语，缺证照类，导致模型临场发挥。
6. **挂起比删除好，编号的挂起比笼统的挂起好。** 删除让信息消失，编号的挂起让下一轮有明确入口。
7. **改写是另一套规则，不能套用回答的规则。** "给推荐""补全信息"这些在回答里对的，在改写里可能是错的——因为你在动别人的东西。
8. **改写时发现原文有矛盾，标出来比抹平好。** 用户需要知道原文不可靠，而不是拿到一份看起来干净的错话。
