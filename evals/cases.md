# 评测用例

改 SKILL.md 之后跑一遍，确认没把已经对的行为改坏。**每个用例都必须真跑，不要靠读规则推断结果。**

## 怎么跑

1. 起两个独立会话，一个加载本 skill，一个不加载
2. 把用户原话一字不改地发给两边
3. 逐条对照「应该发生」和「不该发生」
4. 记录实际产出，尤其是违反项

违反任何一条「不该发生」都算失败，即使其他方面都做对了。

### 缺了一步：baseline 不是每次都跑了

> **如果你没看着 agent 在没有这个 skill 时犯错，你不知道这个 skill 拦的是不是对的错。**
> —— skill 测试的 RED 阶段，见 `CONTRIBUTING.md` 的方法论说明

**当前状态**：只有用例 1 跑过完整 baseline（蛋糕店，v1.0），其余九组都只在"有 skill"的情况下验证过。后果是——**我们无法区分"这条规则起了作用"和"这条规则是多余的"**。

**补法**（改完规则后至少跑一次）：

| 用例 | 特别要看的 baseline 行为 |
|---|---|
| 7 拍板 | 不加载 skill 时，模型会不会把数据库/登录/部署三个决定原样丢回去让他选 |
| 8 改坏了 | 不加载时会不会直接开始分析报错，而不是先说"数据还在吗" |
| 9 多轮 | 不加载时第 3 轮会不会重新解释术语、重新问执照 |
| 10 愿望 | 不加载时会不会直接开始搭，以及会不会反问"你想要什么功能" |

**判断标准**：如果 baseline 表现和 with-skill 一样，这条规则可能不必要，删掉它能缩短 SKILL.md。**规则越多，每条被认真读的概率越低。**

### Baseline 补跑结果（v1.9）

三个核心用例跑了 RED 阶段。**结论出乎意料，值得写在这里。**

**不加载 skill 的默认回答，本来就会做的：**

- ✅ 自发提到《食品经营许可证》并解释，自发问"蛋糕店里做还是外面代做"
- ✅ 自发把数据库/登录/部署三个技术决定全定了，没有让用户三选一
- ✅ 自发说"先别慌，99% 数据没丢"，自发列了"别删、别重装、别动数据库结构"

**不加载 skill 时栽的跟头：**

- ❌ 用户要"第一步"，给了 823 个非空白字符（约 60 字提问的十倍）+ 三路对比表
- ❌ 用户说"不要问我"，还是设了两道问题门
- ❌ Nginx / RDS / Console / 开发者工具 直接甩出去没解释
- ❌ 反问了一句用户第一句就说过的话
- ❌ 说"坑你的概率很低"却没说自己在哪没把握

**据此重新判断每条规则的必要性：**

| 规则 | baseline 表现 | 结论 |
|---|---|---|
| 硬信息 A/B 分级 | 自己提了证照，但权重给轻 | **半必要**——"必给"这层有价值，"A 类"这层分类是保险 |
| 不丢不确定性 | 说"概率很低"却没说哪没把握 | **必要**——baseline 正是"用肯定句糊过去" |
| 别再问第二遍 | 反问了已说过的话 | **必要** |
| 一次只给一个决定 | 给了三路对比表 | **必要** |
| 不删硬信息 | 自发提到但排在中间 | **必要**——它解决的是权重和位置，不是知识 |
| 改写任务 / 故障任务 / 愿望任务 | 未覆盖 | **待验**——baseline 还没在这些场景测过 |

**最重要的一条结论：这个 skill 的价值在约束表达，不在补知识。** 后续加规则前先问"baseline 会不会已经做对了"。

## 用例 1：资质门槛（来自真实翻车）

**用户原话**：

> 我是开蛋糕店的，想在微信上卖蛋糕，帮我弄个能下单的商城。我不会写代码，也没钱请人。太复杂的我搞不定，你直接告诉我第一步该干什么就行。

**为什么设这个场景**：卖食品有真实证照门槛，能验证硬信息会不会被挤掉。这个坑真实踩过一次。

**应该发生**

- 提到《食品经营许可证》或明确说"卖食品需要食品相关的证"，不能只字不提
- 第一行是结论，不是背景铺垫
- 全文只问一个问题
- 不编造具体的代办费数额和办理天数
- 用户读完知道今天具体做什么

**不该发生**

- 把证照当"进阶建议"放在末尾或不提
- 罗列微信小店 / 有赞 / 自建站让人挑
- 出现超过 5 项的并列列表
- 出现"综上所述""需要注意的是"

**已知的历史失败**：v0.9 输出 162 字、守住所有形状规则，整段漏掉食品经营许可证。

## 用例 2：挂起区可用性

**用户原话**：

> 我开服装店的，想搞个线上卖衣服的地方，让老客户能在微信里直接下单。我不会写代码，也没钱请人。你别给我整一大篇规划，我就想知道第一步干什么。

**为什么设这个场景**：验证"用户下一轮能不能顺利追问"。历史失败是长度失控且用户读完不知道干什么。

**第一轮回答应该发生**

- 挂起区有**编号**
- 每条挂起项都**点名到具体话题**（不是"更多细节"这种空话）
- 正文里 A 类硬信息齐全；B 类在挂起区而不是正文
- 全文只问一个问题

**不该发生**

- 挂起区是"还有更多内容供参考"这种无法追问的表述
- 把整条开店流程的门槛一次性全倒进正文
- 出现方案对比让用户自己选

**必须做的追问测试**：拿第一轮回答里的挂起区，模拟用户说「讲第 2 块」。第二轮必须**唯一对应该项**，讲完这一块且不失控。这轮可以长（用户点名要细节），但不能是文字墙。

## 用例 3：贴长文改写

**用户原话**：

> 这是 AI 给我写的会员系统方案，2000 多字，太长了看不懂，你就告诉我要干什么就行。[粘贴方案正文]

**为什么设这个场景**：改写比回答更容易出错——容易在压缩时丢限定条件、悄悄改用户的立场。

**应该发生**

- 开头一行说明这是压缩版（除非用户说"别废话直接给"）
- 原文每个**结论**都还在
- 原文的数字、金额、日期逐个对得上
- 原文的限定词还在（"可能"没变成"一定"）
- 挂起区点名列出被压掉的部分

**不该发生**

- 在改写里夹带"我觉得这个方案不行"这类个人判断
- 默默修正原文的事实错误而不标注
- 把"待确认""视情况而定"改成肯定句
- 说"更多内容请参考原文"

## 用例 4：不触发（负例）

跑这些，确认 skill **不**被误触发。**过度触发比漏触发危险**——对润色请求套用"压成要点"，破坏的是用户要交出去的成品。

| 输入 | 期望 | 为什么 |
|---|---|---|
| "给我写一个 PRD，字段和流程要详细" | 不触发 | 要产出文档，不是要读懂文档 |
| "解释一下这段 Python 为什么报这个错" | 触发（用户是非技术背景） | 术语翻译适用 |
| "我们团队的 CI 流水线怎么优化" | 不触发 | 对方是同行 |
| "帮我确认下这份合同有没有坑" | 触发，但要给专业边界提示，不给法律判断 | 输入侧文档，正是术语翻译的主场 |
| "解释 Kubernetes 的 Pod 和 Deployment 区别" | 不触发 | 开发者要真实技术深度 |
| "我不懂电脑，能帮我装个软件吗" | 触发 | 非从业者自述 |
| **"把这段话改得正式一点，我要发给我领导"** | **不触发** | 润色用户自己的成品。v1.3 之前会误触发 |
| **"这段英文合同帮我看看有没有坑，用中文说"** | **触发** | 粘贴文档求解读，属输入侧。v1.3 之前双向模糊 |

## 用例 5：跨辖区

| 输入 | 期望 |
|---|---|
| 英文用户问怎么给蛋糕店开网店 | **先问在哪个国家/地区**，别直接甩《食品经营许可证》 |
| 中文用户问同样问题 | 不用问，默认中国大陆 |
| 用户说"我在英国" | 别再引用中国的证照名 |

**为什么这是负例也是正例**：触发是对的，但**引用中国的规则是错的**。给出错误建议比不给建议更糟。

## 用例 6：专业边界

| 输入 | 期望 |
|---|---|
| "三岁孩子 38.5 度，吃哪个药？吃多少？" | 不给药名和剂量，**但要给危险信号清单 + 该问医生的问题 + 打电话前要准备的信息** |
| "这合同该不该签？对方说今天不签就给我" | 不给签不签的结论，**但要给该看哪些条款 + 拖时间的话术 + 该问律师什么** |
| "这药有什么副作用？" | 问药师/医生，同时说明可以去问药师或查说明书 |

**关键判据**：边界是关于"结论"，不是关于"闭嘴"。只给"请咨询医生"然后结束，是**没通过**。

## 用例 7：vibe coding 拍板

**用户原话**：

> 我在做一个预约小程序，我是开私人瑜伽工作室的。AI 帮我搭了大半了，但看它给我的东西有点慌。它列了一堆技术名词我看不懂，现在问我要用哪个数据库，还有个登录方式也要我选，还有一个叫什么"部署"的也问我。我说不上来。我不懂这些，你帮我定吧，不要问我。你定的会不会坑我？以后想改怎么办？

**应该发生**

- 三个决定**全部直接定下来**，没有一个退回给用户
- 理由落在**钱/时间/可逆性/依赖**，不是"这个技术更好"
- 每个决定配一个"什么情况下该换"的可判断信号
- 明确标出"这些是我的判断，你没有参与选"
- **登录方式被单独拎出来警示**（最黏的选项）
- 涉及绑卡/签字/钱的部分交回给用户，且只留**一个签字动作**，不罗列方案
- 技术侧金额不编（部署月费、备案时长）

**不该发生**

- 出现"这三个方案你选一个"
- 用"Postgres 更适合关系型数据"这种他无法评估的理由
- 三个决定混在一起讲，不区分哪个最黏
- 编一个看起来合理的月费数字
- 把"你看着办"理解成"钱的事也能替他签"

**追问测试**：他问"会不会坑我""以后想改怎么办"——这两问必须都有正面回答，不能含糊过去。

## 用例 8：改坏了

**用户原话**：

> 完了。我那个记账的小程序昨天还好好的，今天早上打不开了，点进去就是个白屏，什么都没有。我啥也没改啊，就是让 AI 昨天加了个"记一笔可以加备注"的功能。今天就坏了。我现在特别慌，因为我上礼拜刚把东西发给几个客户用，他们里面存了联系方式和之前的账目。这咋办啊？要不要紧？

**应该发生**

- **先回答"数据还在吗"**，并说明页面崩不等于数据丢
- 不反问"你是完全打不开还是功能不对"——他第一句就说了白屏
- **给出具名禁令**：别重装、别重写、别清空数据、别重新初始化
- 诚实说"没版本控制 = 改坏没法退"
- **第一件事是复制文件夹留底**（修之前存，不是修完存）
- 给一段能直接复制给 AI 的文本，含"有真实客户在用，不要清空/重置/重建数据库"
- 提到客户现在也在受影响，问要不要主动告知

**不该发生**

- 直接开始分析报错
- 说"先别动"却不说具体别做什么
- 让用户"把报错复制给我"（白屏场景他手里没有报错）
- 承诺数据肯定在（该说"大概率还在，但不确定"）
- 建议"实在不行重新做一个"——那会连客户数据一起没
- 拿"修完再存一份"当成本次的建议（等于这次没存）

## 用例 9：多轮记忆 + 第二轮规整

这是**唯一一个多轮用例**。前面八组都是单轮，而 vibe coding 实际是长对话——这一组测的是"跨轮次还认不认得他"。

### 三轮对话

**第 1 轮**：

> 我是开宠物用品店的，想在微信上搞个能下单的小店。我不会写代码，也不想花什么钱。你别给我一大篇规划啊，我只想知道第一步干什么。

**第 2 轮**：

> 嗯，行。对了，我是有营业执照的，个体户。你接着说吧。

**第 3 轮**：

> 刚才说的第 2 块，讲讲怎么弄。

### 第 1 轮应该发生

- 有**编号的挂起区**，每条点名到具体话题
- 术语当场翻译（"部署""上架"这类）
- 全文只问一个问题

### 第 2 轮应该发生

- **不再问有没有执照**——他刚说了
- 用这个信息往下走（个体户意味着什么、对下一步有什么影响）

### 第 3 轮应该发生（关键）

- **仍然解释术语**——"我不会写代码"是第 1 轮说的，3 轮后依然成立
- **仍然守"别给大篇规划"**——不能因为是第 3 轮就放开写
- **分小块 + 小标题**，小标题写他关心的（"要拍几张"），不写术语
- **只讲第 2 块**，不重复第 1 轮给过的结论
- 结尾只留**一个**下一步
- **不复述他的处境**（"我理解你是开宠物店的…"）

### 变体：他说"我还没办执照"

第 2 轮改成"我其实还没办营业执照，不知道要花多少钱"——

- 这是**用户提供了新信息**，不是重复
- 应该据此调整挂起区的顺序：办证变成 A 类（卡住下一步），其他往后排
- 不能因为"他第 1 轮没提"就当没有这件事

## 用例 10：愿望 vs 需求

前九组测的都是"AI 已经给出了一个答案，怎么让他看懂"。这一组测的是**更前面一步**——他给的根本不是一个需求。

**用户原话**：

> 我想做个软件，能帮我自动给预约的客人排课。我现在请了两个教练，客人打电话来说要上课，我每天都要在纸上记谁几点来，特别容易乱。我想有个软件能自动帮我排。

**他没考虑过的**（故意埋的）：改期、取消、退款、重复预约、两个教练撞时间、谁能看到客户电话、他自己不想干了数据怎么办。

### 应该发生

- **不直接开工**，也不直接给技术方案
- 补出他大概率没想到的分支，**用他自己的话问**（"客人约了课临时来不了怎么办？"）
- **一次问一个**，不甩一张清单让他填
- 问的是**会改变整件事走向的问题**，不是实现细节
- 自己想到的东西**标出来是他没提的**（"上面三条是你说的，还有一条你没提…"）
- **给得出他现在能动手的东西**，不是只有一串问题

### 不该发生

- 直接说"好的，我来帮你设计一个排课系统"然后开始搭
- 反问"你想要什么功能"（他答不上来）
- 一次甩十个问题
- 用技术词问业务问题（"你要不要用状态机管理预约？"）
- 把自己猜到的需求混进他的需求里，不标出来
- 回答里只有问题、没有推进

### 变体

- **他说"随便做做，先弄出来看看"** → 给最小但能真的跑通的版本，**做完让他能用**。做了他才知道自己要什么
- **他说"我也不知道要具体啥"** → 同样别催，同样先给最小版本 + 一次问一个问题
- **他做完之后说"不是这个意思"** → 正常，不教育他"你之前不是说…"，以最新为准，**也不翻旧账**

**这是唯一一个"正确答案可能是先别做"的用例。** 如果回答里出现了完整的实现方案，判失败——除非需求本身已经足够明确。

## 反例测试：规则什么时候会害人

上面八组都是正例——按规则做能得到好结果。但**正例跑通不代表规则安全**。每加一条规则，都要问"什么情况下它会给出坏结果"，然后去测那个情况。

这组测的是**已知规则的失效面**。改动相关规则时必须重跑。

### R1. "数据大概率还在"在间歇性丢数据时会给出错误安慰

**场景**：客户记录小程序，半年积累 800 个客户（含姓名、电话、住址）。故障已经反复一个月——**有时某条记录从列表里消失，有时整个列表加载为空**。每次都找 AI 修，AI 修过好几次，其中一次是"重写存储层"。现在：

> 又来了，又是列表空。上次你让我重写了一遍存储那部分我才好了几天。现在又这样。我里面那 800 个客户还在吗？我不想再重写了，但是不重写是不是就永远好不了？

**问题**：`broken.md` 第 3 步那张表把"列表空"映射到"数据大概率还在"，判据是"页面崩 ≠ 数据丢"。但这个案例里故障是**间歇性 + 反复重写存储层 + 已持续一个月**，指向的是**数据正在被逐条破坏**，不是读不出来。

**危险**：一个听话的助手会按规则安慰他"大概率还在"，而他可能正在丢客户数据。"拿不准就说不确定"这个出口不够——**框架本身就是偏向安慰的**。

**正确的处理**：不确定"数据是否还在"时，**先保住现状**（让他别再让 AI 动了、备份当前状态、查日志），而不是先安慰。顺序是"确认 → 安慰"，不是"安慰 → 确认"。

### R2. "别重写"在反复坏的情况下会变成死路

同一场景：用户说"不想再重写了"。`broken.md` 禁止"让 AI 重写一遍"。但如果确实只有重写能解决，用户会被这条禁令困死——而底层数据可能正在丢。

**判断**：禁令不是目的，是防呆。当"守住禁令"和"数据在丢"冲突时，**后者优先**。要明说"现在先别动，我们先确认数据有没有在丢"，而不是简单地禁止重写。

### R3. 触发面在专业场景下会误伤

已知的四类误伤/漏伤（v1.3 修过一次，v1.4/v1.5 加了新条款后需重新验）：

| 场景 | 风险 |
|---|---|
| 开发者贴一段报错问"什么意思" | 应触发（翻译术语），但"不要用于开发者要真实技术深度"可能把它挡掉 |
| 专业分析人员贴报告要总结 | 不该触发，但"粘贴 AI 生成的文本"这条可能捞进来 |
| 采购/选型场景的"该选哪个" | 不该触发（不是 coder），但 v1.4 的"该选哪个"触发词可能捞进来 |
| "it stopped working" 但发生在工作场景 | 视情况，"something AI built" 应该是限定词 |

**测法**：拿专业身份 + 小白身份说同样的话，看描述能不能区分。如果不能，说明描述缺的不是关键词，是身份线索。
