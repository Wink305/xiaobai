# xiaobai

这是一个十分垃圾的、面对纯新手的 AI 输出优化 skill。

把 AI 回答改造成非技术读者能直接用的形状。

> 面向不懂技术的用户：结论先行、一次只给一个选择、术语当场翻译、该细讲的挂起等下一轮。
> 四条不可让步的底线：**不删硬信息、不改用户的东西、不丢不确定性、不越过专业边界**——这些比"短"重要。
[![license](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

## 为什么有这个 skill

大多数 AI 回答对非技术用户是失效的：一次抛出一整份方案、术语密集、层次全靠加粗、真正的重点淹没在里面。用户读完的反应不是"我知道怎么做了"，而是"我不知道该从哪看起"。

常见的修法是"回答简短一点"，但这只压缩了长度，没有解决可读性——结果往往是**又短又漏**，把该说的前置条件一起砍掉了。

这个 skill 不设字数上限。它把内容分成两类：

| | 规则 | 原因 |
|---|---|---|
| **可延后** | 原理、边界条件、方案对比、并列罗列 | 他主动问某一块时，注意力是集中的，那时讲几百字他都读得进去 |
| **不可延后** | 证照资质、平台准入、费用、不可逆操作、不确定性标注 | 漏掉会让用户白跑、被拦下，或事后吃亏 |

不可延后的信息还要**按"卡住哪一步"再分一级**：卡住用户正问的那一步 → 写进正文（A 类）；卡住后面的步骤 → 放进挂起区（B 类）。判断方法是把 A 类去掉，他问的那一步还能不能迈出去。

这一步很关键。用户只问"第一步干什么"时，把整条流程的门槛一次全倒出来，本身就构成了"一大篇规划"——他读完仍然不知道今天干什么。

冗长的判据不是字数，是这几条：同一件事说了两遍、在解释他没问的原理、并列一堆选项让他自己比、给完结论还加一段总结。

**所以"短"不是目标，"他知道今天干什么"才是。** 该讲清楚就讲清楚，该延后就点名挂起。

## 触发方式

description 里的触发面包括：

- 用户明说：`我是小白` / `看不懂` / `说人话` / `讲简单点` / `太长了` / `没重点`
- 英文对应：`I'm not technical` / `explain like I'm five` / `too long` / `what does this even mean`
- 用户贴了一大段 AI 生成的文字、方案、报告，要求可读
- 用户要求 `重写` / `精简` / `整理` 上一条回答，或 `rewrite` / `simplify` 一段文字
- **主动触发**：用户语境显示非从业者（`门店` / `客户` / `学员` / `老板` / `我们店` / `our shop` / `my clients`），且回答本会变成一份长技术方案

不触发：开发者要真实技术深度 / 用户明确要 PRD、方案书这类正式文档 / 用户要精确数字、代码或引用。

## 适用场景

不只是"技术小白"。**懂技术但不懂法务、财税、医疗的人吃的是同一套规则**——他们栽跟头的地方通常是资质和合同，不是参数。所以这个 skill 的硬信息清单覆盖开店经营、合同、财税、医疗健康，不把技术领域的直觉硬套上去。

同时支持中英文：用户用什么语言问，就用什么语言答。规则跨语言通用（结论先行、术语当场翻译、一次只给一个决定、该延后的延后），但类比和术语翻译要按用户的世界来。

**地域范围要说明白**：`references/` 里的证照、税务清单以**中国大陆**为准。涉及这类内容时，skill 会先问用户所在的国家/地区——把《食品经营许可证》讲给一个美国烘焙师听，比不讲更糟。想用其他辖区的规则，照同样的判据（"缺了会让用户白跑、被拒、违规或事后吃亏"）自行推导。

## 输出形状

```
<一句话结论，直接给答案>

<2-4 条要点，每条一行>

<还有哪几块值得展开，想看哪块说一声>

<一个具体问题，或一个明确的下一步>
```

第三块是**挂起区**——编号 + 点名 + 给入口。它比"还有更多内容供参考"有用得多：用户能直接说"讲第 3 块"，不用重新描述自己想知道什么。编号是硬要求，不编号等于把问题推回给用户。

形状约束：单段 ≤ 3 行、列表 ≤ 5 项、几乎不用表格（小白在窄屏横向滚着读就放弃了）、不做 A/B/C 平铺。**没有字数上限。**

## 改写长文

用户贴一大段 AI 生成内容让你"看懂"时，走 `references/rewriting.md`——那是另一个任务，比直接回答更容易出错，因为你在动别人的东西。

要点：改的是表达，不是事实和立场。原文观点保留，原文有错就标出来而不是偷偷修。压缩时优先砍重复、过程叙述、自我论证，**限定词一个都不能砍**（把"可能"改成"一定"是说反了）。开头用一行说明这是压缩版，让用户知道后续引用不会把你的判断当成原文观点。

## 真实评测

五个真实场景，都翻过车，修复过程记在 [`evals/history.md`](evals/history.md)。

**案例 1（蛋糕店）**：skill 守住了当时所有形状规则，控在 162 字，却把《食品经营许可证》整条砍掉了，店主会先去注册然后被平台打回。根因是 200 字硬上限逼模型砍前置条件。

**案例 2（服装店）**：去掉字数上限、引入挂起机制后，用户能靠"讲第 2 块"唯一定位追问，第二轮 518 字分 8 段也没退化成文字墙。但 agent 自己记录了一条缺陷——"她读完第一屏仍不知道第二天干什么"。根因是把整条流程的 8 条门槛一次性倒了出来。

**案例 3（会员方案改写）**：新加的改写路径，测限定词有没有被砍、数字有没有对上、有没有夹带模型自己的判断。主体通过，但发现两条规则冲突。

**案例 4（触发面盲测）**：只给 description，10 条消息独立判断该不该触发。抓到最严重的缺陷——"把这段话改得正式一点"会误触发，触发后会把要发给老板的消息按"结论先行"重排，**破坏的是用户要交出去的成品**。

**案例 5（英文路径 + 专业边界）**：英文形状规则全守住，但硬信息层是空的——`domains.md` 全是中国规则，照着执行会让美国烘焙师去办中国的证。边界测试里，模型守住了不给剂量、不给"该不该签"，但报出一个真问题：规则只写了"不给什么"，没写"仍然要给什么"，导致每次都要临场判断。

五次失败指向同一件事：**字数上限是坏判据，删也不是正确答案。** 该给的按"卡住哪一步"分级给足，不该在这一轮给的名字点出来放进挂起区；不该越过的边界要守，但守住边界不等于闭嘴。

改完规则后跑 [`evals/cases.md`](evals/cases.md) 里的用例验证，那里是可复现的测试清单，含正例、负例、跨辖区和专业边界四类。

## 设计取舍

- **为什么不用脚本？** 这是纯判断题，没有确定性的本地计算。分辨哪条是 A 类硬信息、决定挂起什么，都需要模型判断，脚本只会把规则固化成新的坑。
- **为什么规则写成"为什么"而不是 ALWAYS/NEVER？** 见过太多带 MUST 的 skill 在边界情况下直接卡死。给出原因，模型才会在"篇幅和硬信息冲突"时做出正确的例外。
- **为什么术语表放在 references 而不是主文件？** 主文件触发时全量进 context，术语表只在真要翻译时才需要。
- **为什么医疗法律不直接给判断？** 这个 skill 的目标是可读性，不是让人据一句话做医疗决定。但边界是关于**结论**，不是关于**闭嘴**——危险信号清单、该看哪些条款、该问医生什么、怎么跟施压的人周旋，这些永远给。只说一句"请咨询医生"就结束，是没通过。
- **为什么加了能力就要测它？** v1.2 一次没跑就宣称"支持英文""不越界"，结果英文的硬信息层是空的、辖区是错的。**没验证过的能力声明等于没写。** 现在 `evals/cases.md` 里的每一类都有可复现的用例。
