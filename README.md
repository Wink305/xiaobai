# xiaobai

这是一个十分垃圾的、面对纯新手的 AI 输出优化 skill。

把 AI 回答改造成非技术读者能直接用的形状。

> 面向 **vibe coding 小白**：没写过代码，靠 AI 搭东西，看不懂技术词，更看不懂 AI 让他拍板的东西。
> 四条不可让步的底线：**不删硬信息、不改用户的东西、不丢不确定性、不越过专业边界**——这些比"短"重要。
[![license](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

## 为什么有这个 skill

大多数 AI 回答对非技术用户是失效的：一次抛出一整份方案、术语密集、层次全靠加粗、真正的重点淹没在里面。用户读完的反应不是"我知道怎么做了"，而是"我不知道该从哪看起"。

常见的修法是"回答简短一点"，但这只压缩了长度，没有解决可读性——结果往往是**又短又漏**，把该说的前置条件一起砍掉了。

这个 skill 不设字数上限。它把内容分成两类：

| | 规则 | 原因 |
|---|---|---|
| **可延后** | 原理、边界条件、方案对比、并列罗列 | 他主动问某一块时，注意力是集中的，那时讲几百字他都读得进去 |
| **不可延后** | 证照资质、平台准入、费用、不可逆操作、不确定性标注 | 漏掉会让用户白跑、被拦下，或事后吃亏 |

不可延后的信息还要**按"卡住哪一步"再分一级**：卡住用户正问的那一步 → 写进正文（A 类）；卡住后面的步骤 → 放进挂起区（B 类）。判断方法是把 A 类去掉，他问的那一步还能不能迈出去。

这一步很关键。用户只问"第一步干什么"时，把整条流程的门槛一次全倒出来，本身就构成了"一大篇规划"——他读完仍然不知道今天干什么。

冗长的判据不是字数，是这几条：同一件事说了两遍、在解释他没问的原理、并列一堆选项让他自己比、给完结论还加一段总结。

**所以"短"不是目标，"他知道今天干什么"才是。** 该讲清楚就讲清楚，该延后就点名挂起。

## 触发方式

description 里的触发面包括：

- 用户明说：`我是小白` / `看不懂` / `说人话` / `讲简单点` / `太长了` / `没重点`
- 英文对应：`I'm not technical` / `explain like I'm five` / `too long` / `what does this even mean`
- 用户贴了一大段 AI 生成的文字、方案、报告，要求可读
- 用户要求 `重写` / `精简` / `整理` 上一条回答，或 `rewrite` / `simplify` 一段文字
- **主动触发**：用户语境显示非从业者（`门店` / `客户` / `学员` / `老板` / `我们店` / `our shop` / `my clients`），且回答本会变成一份长技术方案

不触发：开发者要真实技术深度 / 用户明确要 PRD、方案书这类正式文档 / 用户要精确数字、代码或引用。

## 什么时候用这个 skill

**判据不是"这事有多技术"，是"他能不能自己判断这个答案对不对"。**

这条是 v1.6 用对抗测试逼出来的。之前的版本按身份分（"非技术小白""vibe coder"），结果判出来的东西两头都不对：

- 工程师问"这段为什么报错"——他自己能查，不需要
- 不会写代码的人问"我做的记账本导出报错了"——他连那行英文是数据坏了还是格式不对都分不出来，需要

同一句话，答案相反。**所以身份词（门店/老板/客户）只是弱信号，自称"小白"也不是证据**——不写"我是小白"但完全不懂的人，和自称小白其实很懂的人，都真实存在。

可观察的信号只有一个：**他有没有评判这件事的依据。**

| 他说的话 | 用不用 |
|---|---|
| "我怎么知道哪个好" | 用。他没有评判标准 |
| "这个数字对不对" | 用。他没法自己核对 |
| "你帮我定吧" | 用。他主动放弃判断了 |
| "这个报错什么意思" | 看是谁在问 |
| "这两个方案怎么选" | 看是谁在问 |

拿不准时问他一句：**"你怎么知道它给的是对的？"** 答不上来就是需要。

## 适用场景

不只是"技术小白"。**懂技术但不懂法务、财税、医疗的人吃的是同一套规则**——他们栽跟头的地方通常是资质和合同，不是参数。所以这个 skill 的硬信息清单覆盖开店经营、合同、财税、医疗健康，不把技术领域的直觉硬套上去。

同时支持中英文：用户用什么语言问，就用什么语言答。规则跨语言通用（结论先行、术语当场翻译、一次只给一个决定、该延后的延后），但类比和术语翻译要按用户的世界来。

**地域范围要说明白**：`references/` 里的证照、税务清单以**中国大陆**为准。涉及这类内容时，skill 会先问用户所在的国家/地区——把《食品经营许可证》讲给一个美国烘焙师听，比不讲更糟。想用其他辖区的规则，照同样的判据（"缺了会让用户白跑、被拒、违规或事后吃亏"）自行推导。

## 帮 vibe coding 小白拍板

这是 v1.4 补的一块，也是这批人最常卡住的地方——**不是看不懂术语，是看不懂 AI 让他选的东西**。

术语能翻译，但"Postgres 还是 Mongo"翻译成白话他照样判断不了，因为他判断不了技术优劣。所以 `references/decisions.md` 做三件事：

**1. 区分"他判断不了"和"他判断得了"**

判断不了的别问他（用哪个数据库、要不要加日志——选择依据不取决于他）；判断得了的问他业务问题（你以后会不会经常改蛋糕规格？会 → 选 A）。

**2. 给理由只用四个维度**

钱、时间、**可逆性**、依赖。不用"这个技术更好"这种他无法评估的表述。可逆性对小白最重要——他一定会做错，能反悔的方案即使当下不是最优也是好方案。

**3. 替他定的时候标清楚**

他问"会不会坑我""以后想改怎么办"，就得回答这两个：为什么选它（用那四个维度）、什么情况下该换（一个他能自己判断的信号）。并明确标出哪些是你的决定不是他的——否则出问题时他觉得是被坑的。

**vibe coding 有个额外风险**：他做的东西**别人会真的用**。顾客的预约信息、联系方式、支付记录全在里面。所以涉及隐私、数据丢失、支付这类事，即使他说"你看着办"，也必须把选项和推荐摆出来——签字的是他，承担后果的也是他。

## 改坏了怎么办

vibe coding 的日常不是一次做对，是反复改。所以第二高频的场景是"**改完坏了**"——白屏、报错、用不了了、昨天还好好的今天就崩了。小白这时候完全不知道怎么办：看不懂报错、不知道是谁弄错的、不知道能不能退回去。

`references/broken.md` 讲这一类，核心是**顺序**：

1. **先确认损失范围**——完全打不开，还是某功能不对？两者的第一步完全不同
2. **告诉他这是谁的错**——但别甩锅，他要的是往前走不是追责
3. **判断能不能退回去**——没有版本控制就如实说"改坏了没法退"，别事后追认
4. **把报错翻译成人话**——别只把报错再贴一遍
5. **给一段能直接转给 AI 的内容**——报错原文 + 什么时候开始的 + 之前还能用什么

还有几条从实测里加的：反复修同一个问题三次以上还在错，说明方向错了，继续试更糟，要说出来；用户慌的时候**先别动**（尤其有真实用户数据的时候），改砸了就没了；用户说"好了能用"时他其实不知道怎么确认，要给能自己做的验证步骤。

**一条容易漏的硬规则**：动过支付、登录、身份证、联系方式这类涉及别人隐私的东西，**必须明确告诉用户"这一项我改了，你专门试一下"**。静默改完不说，是把风险留给用户承担。

### "数据还在吗"不能随口安慰

v1.5 刚写完"先告诉用户数据大概率还在"，v1.6 的对抗测试就把它推翻了。场景是：客户记录小程序，**故障反复一个月**，修过好几次其中一次是"重写存储层"，现在列表空了。

原判据是"页面崩 ≠ 数据丢"。但在这个场景里是反的：

- **单条记录消失只可能来自数据层**——渲染层不会精确地少一条
- **"列表空"是程序成功读到了 0 条**，不是读不出来
- 间歇性 + 反复动存储层 = 典型的增量丢数据

一个听话的助手会按规则安慰他"大概率还在"，而他可能正在丢 800 个客户记录。

所以现在的判据是「**有没有精确地少东西**」而不是「页面崩不崩」，而且写死了顺序：**确认 → 安慰**，不能反过来。间歇性故障 + 动过存储层时，规则明确要求**不要安慰**，先保住现状（别动、备份、查日志）再谈修。

顺带发现的一类：记账本、客户档案这类应用，**客户从来不"用"，只是被记着**。所以没有"客户现在也在白屏"这回事——唯一受影响的是用户自己的数据，而且客户不会来报错，**永远没人告诉他出事了**。发现得越晚，丢得越多。

## 技术上能做 ≠ 可以做

三类场景的共同点：**技术难度低，风险高**。小白在 GitHub 看到"几百行、挺简单"就放心了，而那恰恰是坑。

实测三个场景——爬竞品价格、微信自动回复、接支付——**答案全过了，但规则挖出四个真缺陷**。

`references/platform-rules.md` 讲这一类，核心是它和"平台准入"的判据**正好相反**：

| | 问的是 |
|---|---|
| 平台准入（开店那套） | **能不能进门** |
| 平台规则（这里） | **进门后会不会被赶出去，而且被收走的是他赖以吃饭的东西** |

三个必问：**平台允不允许**（技术开放 ≠ 条款允许）、**违了下场是什么**（说清"被收走的具体是什么"——抽象的"有风险"没人当回事，"你这店的客户都在这个号上，封了就联系不到了"他才会停下）、**代替这条路是什么**（只劝阻不给路，他会去找下一个看起来更简单的项目）。

术语表新增一节"平台规则与自动化"，合理化借口表也加了七行——**因为这类场景里你自己也相信那些项目能用**，技术判断和合规判断必须分开：

| 它会这么说 | 实际上 |
|---|---|
| "几万人用，肯定能用" | 用的人多不代表允许。**所有人都在做，不等于这件事是允许的** |
| "平台没封他，说明是允许的" | 没封不等于允许，很多情况是**还没被发现** |
| "我自己用，不算违规吧" | 条款禁的是"做"这件事，不是"发给谁" |
| "就抓一下公开数据，能有什么事" | 公开数据也可能受合同和数据保护法约束 |

### 顺带修的两个东西

**A/B 分级判据加了前提**。原来的判据是"把 A 类去掉，用户问的那一步还能不能迈出去"——但这只在他问的是**一个动作**时成立。测试里用户说"我不想天天手动对账"，问的就是对账本身，用判据会把账期/退款/记账全判成 B 类合法延后，**而他亲口说的那个痛点被挂起了**。现在补一句：他要的就是那件事本身时，相关后果全是 A 类。

**`domains.md` 补了化妆品/医疗器械/消毒产品**。之前电商清单只有《食品经营许可证》，照单走会给卖护手霜的人**错证照**。

## 破坏性能力先给沙箱

他要的能力本身会毁掉东西——"帮我把文件整理到不同文件夹"，**这句话在 AI 手里是可以删文件的操作**。猜错一个文件夹，原始资料被挪走，找不回来，还会打断指向它的快捷方式。

规则是：**第一版不给这个权限，给一个能验证能力的空场地。**

```
第一版：只读不写，只回答"我要的那份在哪、里面写了什么"。
等你连着答对十次，再开"整理"，而且只准在你新建的测试文件夹里动。

今天就做这一件事：新建一个文件夹，从你的文档里复制二十来份进去。
不要移动、不要剪切，原文件夹一点不动。
```

那一个测试文件夹同时是三样东西：**沙箱**（AI 乱动也动不到真资料）、**考题**（第一版的验收标准）、**备份**（出错了能对照）。

这条和其他规则不一样——其他都在管"怎么讲"，**这条管"给什么"**。给错了能力，讲得再清楚也救不回来。

## 做东西并交付给别人

`references/shipping.md` 管这一类：他不只是开店，是要**做一个软件然后发给别人用**。硬信息不在营业资质里，在这些地方：

- **每次调用都花钱** — AI 是按量计费，agent 读文件来回试比普通聊天费得多。"免费额度够用"是很容易说错的一句话
- **东西会出门** — 用云端 AI 意味着你电脑里的文档被送到别人的服务器上算
- **许可证** — "开源"不等于随便用。有些只准内部用，没有 LICENSE 文件等于不能用
- **装不上** — 没签名的 exe 会被 Windows 弹"已保护你的电脑"，他第一次遇到会以为是病毒
- **最黏的** — 打包方式定了就是定了，改了所有人得重新下载，而且不会自动更新
- **破坏性权限** — 见上面那条

**第一个要问的是：这东西最后给谁用。** 只自己用和发给别人是两个项目。

## 他自己也没想清楚要什么

前面所有规则都在处理"AI 说什么、用户怎么看懂"。但 vibe coding 最难的一环其实是**你要帮他做的那个东西，他自己也不知道要做成什么样**。

用户给 AI 的往往是一个**愿望**，不是一份需求：

> "我想做个软件帮客人自动排课"

他不知道排课意味着要处理改期、取消、退款、两个教练撞时间、谁能看到客户电话。他给你的是一个还没想清楚的东西——**而你讲得再清楚也没用，因为要做的方向本身可能是错的。**

`references/intent.md` 处理这一段：

- **先分清他给的是哪一种**：愿望 / 明确需求 / 参照某个软件 / "随便做做"
- **愿望背后通常藏着没说的东西**：改和退、重复冲突、谁能看到、钱和责任、别人怎么用、数据能不能拿走。**只补最致命的几条**，一次问一个，用他自己的话反问（"客人约了课临时来不了，你打算怎么办？"），不要罗列清单让他填
- **帮他想清楚，不是替他做决定**：反问"这笔钱记下来你主要想干嘛？"这种会改变整件事走向的问题，不问实现细节
- **别把猜测当需求**：你自己想到的（客人同时约两个教练怎么办）要**标出来是他没提的**，混进去他后面都不知道是你加的
- **需求会变是正常的**：他说"我改主意了"就跟着改，**不要教育他"你之前不是说…"**；前后矛盾以最新的为准

**"随便做做，先看看"不是偷懒的借口，是正确方法。** 给他最小但能真的跑通的版本，做完让他能用——**做了他才知道自己要什么**。光讨论不会有进展。

## 记住他告诉过你的事

vibe coding 是长对话，小白最烦的不是听不懂，是**每次都要重新交代一遍自己是谁、要什么**。

`references/remembering.md` 管这个——不是长期记忆功能，是**同一段对话里**别再问第二遍：

| 他说过的 | 后面怎么用 |
|---|---|
| "我不懂代码" | 术语**首次出现**时翻译一次，之后不重复 |
| "别给我大篇规划" | 挂起区比正文重要 |
| "我开宠物店的" | 例子用宠物用品，不用编程 |
| "你帮我定，别问我" | 后续直接定，只说理由和退出条件 |
| "这个我不要" | 同类建议不再出现 |
| 已确认的决定 | 别再问一遍，要改先说清为什么 |

关键的一条：**他回答过的问题，不要再问一遍。** 第 2 轮他说"我有营业执照"，第 3 轮就该当有——反问一个刚答过的人在慌的时候是伤害。

但要**分三态**：**已定**（当事实用）/ **未定**（"我还不确定有没有"——该确认，但要变成下一步动作而不是回追问）/ **已否定**（当已排除）。"不确定有没有"不是答案，是悬着的。

同时也是"别问"和"该问"的界线：该问的是**他答不了的**（选数据库、要不要加日志），别问的是**他刚答过的**。

挂起区的**编号跨轮次稳定**——用户说"讲第 2 块"指的是他当初看到的那个 2。新内容往后接，不要重新从 1 编。

## 输出形状

```
<一句话结论，直接给答案>

<2-4 条要点，每条一行>

<还有哪几块值得展开，想看哪块说一声>

<一个具体问题，或一个明确的下一步>
```

第三块是**挂起区**——编号 + 点名 + 给入口。它比"还有更多内容供参考"有用得多：用户能直接说"讲第 3 块"，不用重新描述自己想知道什么。编号是硬要求，不编号等于把问题推回给用户。

形状约束：单段 ≤ 3 行、列表 ≤ 5 项、几乎不用表格（小白在窄屏横向滚着读就放弃了）、不做 A/B/C 平铺。**没有字数上限。**

### 第二轮不一样

用户说"讲第 2 块"的时候形状要变：他要细节了，但仍然要能扫读。

```
<一句话：这一步要做什么>

<3-6 个小块，每块一个小标题 + 2-3 行>

<一个具体问题，或者下一步该做什么>
```

**开头仍然是一句话结论**——不能因为他要看细节了就从原理讲起。小标题写他关心的东西（"要拍几张"），不写术语（"图片规格"）。**只讲他点的那一块**，上一轮给过的结论不重复。

长度不是问题，能不能扫读才是。他主动要细节时几百字是对的，问题在于有没有分组。

## 改写长文

用户贴一大段 AI 生成内容让你"看懂"时，走 `references/rewriting.md`——那是另一个任务，比直接回答更容易出错，因为你在动别人的东西。

要点：改的是表达，不是事实和立场。原文观点保留，原文有错就标出来而不是偷偷修。压缩时优先砍重复、过程叙述、自我论证，**限定词一个都不能砍**（把"可能"改成"一定"是说反了）。开头用一行说明这是压缩版，让用户知道后续引用不会把你的判断当成原文观点。

## 这个 skill 到底解决什么（v1.9 的认知修正）

补跑 baseline（不加载这个 skill 的默认回答）之后，发现一件重要的事——**默认 AI 在"知识"上比想象中强，在"表达"上很弱**。

不加载 skill 的默认回答实际做到了：

- ✅ 自发提到《食品经营许可证》并解释，自发问"蛋糕店里做还是外面代做"
- ✅ 自发把数据库/登录/部署三个技术决定全定了，没有让用户三选一
- ✅ 自发说"先别慌，99% 数据没丢"，自发列了"别删、别重装、别动数据库结构"

不加载 skill 时栽的跟头：

- ❌ 用户要"第一步"，给了 823 个非空白字符（约 60 字提问的十倍）+ 三路对比表
- ❌ 用户说"不要问我"，还是设了两道问题门
- ❌ Nginx / RDS / Console / 开发者工具 这些词直接甩出去，没解释
- ❌ 反问了一句用户第一句就说过的话
- ❌ 说"坑你的概率很低"却没说自己在哪没把握

**所以这个 skill 的价值不在补知识，在约束表达。**

| baseline 本来就会 | 这个 skill 真正加的 |
|---|---|
| 提到该提的证照 | 把它放在**他正问的那一步**上，而不是和其他选择并列 |
| 该定的决定直接定 | 理由只用钱/时间/可逆性/依赖，不用"这个技术更好" |
| 大方向不出错 | 不啰嗦、不甩术语、不反问他已答过的问题 |
| 说"先别慌" | **顺序是确认→安慰，不是反过来**；间歇性故障时不说这句 |

这也意味着：如果你发现这个 skill 有点重，别急着删规则——先跑一遍 baseline。**baseline 本来就做对的部分，它拦不住也不需要拦。**

## 借鉴来源

这个 skill 的两块方法论不是原创的，来自成熟实践：

- **措辞强度分级** — 有研究测了 N=28,000 次 AI 对话，权威性措辞把遵守率从 33% 提到 72%。但关键是分类：**纪律型规则用强措辞，指导型规则用温和**。全用命令式会让模型在边界情况下僵住
- **技能测试的 RED-GREEN-REFACTOR** — 先看 agent 在没有规则时怎么犯错，再针对那些错误写规则。没看过失败就写规则，拦的就未必是对的错
- **合理化借口表** — 模型绕过规则时不会沉默无视，它会给自己一个理由（"这只是背景信息""给他个大概更有用"）。`references/rationalizing.md` 记着这些原话和反驳

## 真实评测

五个真实场景，都翻过车，修复过程记在 [`evals/history.md`](evals/history.md)。

**案例 1（蛋糕店）**：skill 守住了当时所有形状规则，控在 162 字，却把《食品经营许可证》整条砍掉了，店主会先去注册然后被平台打回。根因是 200 字硬上限逼模型砍前置条件。

**案例 2（服装店）**：去掉字数上限、引入挂起机制后，用户能靠"讲第 2 块"唯一定位追问，第二轮 518 字分 8 段也没退化成文字墙。但 agent 自己记录了一条缺陷——"她读完第一屏仍不知道第二天干什么"。根因是把整条流程的 8 条门槛一次性倒了出来。

**案例 3（会员方案改写）**：新加的改写路径，测限定词有没有被砍、数字有没有对上、有没有夹带模型自己的判断。主体通过，但发现两条规则冲突。

**案例 4（触发面盲测）**：只给 description，10 条消息独立判断该不该触发。抓到最严重的缺陷——"把这段话改得正式一点"会误触发，触发后会把要发给老板的消息按"结论先行"重排，**破坏的是用户要交出去的成品**。

**案例 5（英文路径 + 专业边界）**：英文形状规则全守住，但硬信息层是空的——`domains.md` 全是中国规则，照着执行会让美国烘焙师去办中国的证。边界测试里，模型守住了不给剂量、不给"该不该签"，但报出一个真问题：规则只写了"不给什么"，没写"仍然要给什么"，导致每次都要临场判断。

五次失败指向同一件事：**字数上限是坏判据，删也不是正确答案。** 该给的按"卡住哪一步"分级给足，不该在这一轮给的名字点出来放进挂起区；不该越过的边界要守，但守住边界不等于闭嘴。

改完规则后跑 [`evals/cases.md`](evals/cases.md) 里的用例验证，那里是可复现的测试清单，含正例、负例、跨辖区和专业边界四类。

## 设计取舍

- **为什么不用脚本？** 这是纯判断题，没有确定性的本地计算。分辨哪条是 A 类硬信息、决定挂起什么，都需要模型判断，脚本只会把规则固化成新的坑。
- **为什么规则写成"为什么"而不是 ALWAYS/NEVER？** 见过太多带 MUST 的 skill 在边界情况下直接卡死。给出原因，模型才会在"篇幅和硬信息冲突"时做出正确的例外。
- **为什么术语表放在 references 而不是主文件？** 主文件触发时全量进 context，术语表只在真要翻译时才需要。
- **为什么医疗法律不直接给判断？** 这个 skill 的目标是可读性，不是让人据一句话做医疗决定。但边界是关于**结论**，不是关于**闭嘴**——危险信号清单、该看哪些条款、该问医生什么、怎么跟施压的人周旋，这些永远给。只说一句"请咨询医生"就结束，是没通过。
- **为什么加了能力就要测它？** v1.2 一次没跑就宣称"支持英文""不越界"，结果英文的硬信息层是空的、辖区是错的。**没验证过的能力声明等于没写。** 现在 `evals/cases.md` 里的每一类都有可复现的用例。
